Voxel One native iPhone client

This is a UIKit/SceneKit app, rendered natively through Apple's graphics stack.
It does not open the desktop game in Safari or stream desktop screenshots.
The native client supports offline sandbox building with fractional/model geometry and online
Voxel One sandbox / Voxel City One through the Java mobile gateway.

Phone controls

Hold the four direction buttons to walk. Drag the world to look. Break and Place
use the selected hotbar stack. Hold Jump to jump again after landing. Scroll the
hotbar to reach all nine slots. Bag swaps a stack into the selected hotbar slot. Pause stops local input;
online simulation keeps running. Menu signs out of online play.

Offline sandbox starts from Terrain.DEFAULT_SEED, generator version 3, exported
by the actual Java Terrain and WorldVoxels code. The local area has 49 by 49
columns. It includes a starter inventory. Breaking collects a whole block into
the local inventory; placing consumes one. Saves are atomic, live in the app's
Application Support directory, and resume on cold launch. New world asks before
replacing that save. Saves are separate from Java offline-city.dat / offline.dat;
this release does not import desktop saves or simulate an offline city.

Online sandbox keeps the existing game server's inventory, health, item drops,
authentication, multiplayer edits and crafting rules. The initial phone UI exposes
walking, jumping, whole-block edits, hotbar and inventory swaps. The desktop model
editor, mounts and specialized transport or finance tools are not exposed by
this phone UI. Craft now has a searchable, category-filtered book of all104 shared recipes,
including cut/join, flower pots, sticks and eight tools. Offline uses the app catalog;
online shows the gateway catalog, so an older gateway may offer fewer recipes.
Shared itemsVersion1 defines199 inventory IDs. Tools stack at1, sticks at64;
item-only tools cannot be placed as terrain. Held-tool models/equipment pose and
offline overflow drops remain follow-up work. No mining/combat bonus is added.
New clients request itemsVersion1 at login. Older clients receive block recipes;
if item-only inventory requires an update, the gateway returns a fixed upgrade error.
Batch selects1–64 recipes per transaction; costs/output update together. Online
batches require gateway batchCrafting capability; older gateways stay at1.
Offline insufficient ingredients or output space reject the entire batch.
Owned/required ingredients appear on each row; missing ingredients or a full bag
leave inventory unchanged. Crafting stops local movement while the book is open.

Online city starts in an isometric planning view. Plan/Walk switches views.
Two fingers pan; pinch zooms. Tool selects Inspect, Dirt road, Residential,
Commercial, Industrial or Agricultural. Tap ground for corners, or Point enters
a precise X/Z grid coordinate. Undo removes the latest corner. Confirm sends the
plan to the actual city server. Roads need two endpoints; zones need at least
three convex corners. The server checks costs, zones, players and bounds.
Clock, treasury, roads, zone overlays, buildings and citizens come from actual
CityFrame snapshots. Inspect near a citizen shows their activity, hunger and cash.
The city, roads and accounts are shared with desktop users; no phone balance or
population is synthesized. Planning focus does not teleport the player's avatar.

Build on a Mac

Requires Xcode with an installed iPhone Simulator runtime and Java 17+/Maven
for the gateway's isolated integration tests. No Apple account is needed for
simulator builds. The controller's exact-source check runs:

  bash ios/check-simulator.sh SIMULATOR_UDID ABSOLUTE_EVIDENCE_DIRECTORY SOURCE_HEAD

The contract is documented in tools/ios/README.md. The script checks the exact
Git head and clean tracked source, starts two fresh Java game worlds with
in-memory synthetic accounts, generates an unsigned Xcode project in ios/build,
builds the actual app, installs it and runs XCTest using normal UIKit controls.
No source is rewritten while testing. Failed builds return sanitized compiler
or assertion diagnostics; raw logs, TLS keys and account state stay out of evidence.

For manual simulator play:

  python3 ios/make-project.py
  open ios/build/VoxelOne.xcodeproj

Choose the VoxelOne scheme and an iPhone Simulator. Run the app and choose New
offline sandbox. For a physical phone, use your own Mac and Apple account/team,
change the app target's CODE_SIGNING_ALLOWED to YES and configure Signing &
Capabilities before building to your connected iPhone. TestFlight/App Store
publication and physical-device signing are separate steps; this check does not
publish, sign for distribution, or prove physical-device performance.

Online service

Run the gateway alongside existing game servers. It connects to those servers
as ordinary clients using administrator-supplied SHA-256 certificate fingerprints.
Use the full client JAR on its classpath (the main class is explicitly the gateway;
no graphical window is opened):

  java -cp target/voxel-one-1.0-SNAPSHOT-client.jar dev.jayms.net.mobile.MobileGateway \
    --server 127.0.0.1 --sandbox-port 25565 --city-port 25566 \
    --sandbox-pin PUBLIC_SANDBOX_CERTIFICATE_FINGERPRINT \
    --city-pin PUBLIC_CITY_CERTIFICATE_FINGERPRINT --listen-port 25567

The gateway binds loopback only. Provide a normal, trusted HTTPS reverse proxy
for /mobile/v1/ to that loopback port before using it from a phone. Keep the proxy
from logging request bodies or Authorization headers. This feature does not deploy
a proxy or alter the current live services. Enter that HTTPS origin in the native
app, choose Sandbox or City, then sign in or create an account on that game server.
The phone uses standard system TLS trust. HTTP is accepted only for localhost
simulator fixtures; remote cleartext URLs are rejected by the app.

The gateway never reads an account database. Passwords are forwarded only through
the existing pinned-TLS login path, and no credentials are retained by the app.
Bearers are memory-only, expire after 15 idle minutes and are revoked on logout.
There are at most 32 sessions and 4 concurrent logins. Sign-in attempts are capped
at 10 per minute per backend peer address; a loopback reverse proxy shares that
limit. JSON requests are bounded to 8 KiB; snapshots use the player's surrounding
33 by 33 columns and stream as the player or planning focus moves. Action replies
wait for server receipts; a timed-out action is not automatically retried.

Offline flight

Fly toggles collision-aware flight in the local Sandbox. Hold Jump to rise and
Down to descend. Let go to hover. Walk restores gravity. Movement remains bounded
to the loaded area and known snapshot ceiling. Flight mode resets to walking on
world load; the saved position is retained. Pause, menu, graphics and backgrounding
clear held input. Online flight is unavailable pending authoritative protocol work.

Sandbox cameras

Camera selects First person, Third person or Isometric. The choice survives app
restart. Third person shows a simple local player capsule; its lens retracts near
solid terrain. Isometric uses two fingers to pan and pinch to zoom. Walk input
recenters the overview on the player. Tap terrain to aim, then Break or Place.
A camera overview does not extend the player's five-block reach or see through
walls for edits. City keeps its existing Plan/Walk controls. Orientation changes
cancel held movement and reset the aim point.

Detail contract

Snapshot schema 2 carries contract version 1, material IDs and subdivisions from
Java Blocks, model fingerprints/colored octree leaves, and per-cell fractional
leaves. Native drawing, collision and ray picking use those boxes. Models keep their
8/16/32 resolution; fractional world cells use 16. Missing detail or budget overflow
is rejected, never replaced by a whole cube. Limits: 512 partial cells and 32,768
expanded model/fractional leaves per snapshot. New offline worlds include two
flower pots and eight half-size dirt cubes for normal building. Old local schema 1
saves migrate to the bundled contract while keeping their terrain and inventory.
Uniform fractional regions can be collected at any supported grid depth. Pieces
place against the exact aimed face, including another empty region in the same cell;
filled regions merge back into full cells. Full tool and crafting parity is pending.

Regenerate the checked-in contract from the authoritative Java definitions:

  java -cp target/classes dev.jayms.net.mobile.MobileSnapshot --contract ios/Resources/contract.json

Save worker

Offline changes capture value-only world data on the main thread. A serial utility
worker builds the save snapshot, validates it, encodes JSON and atomically replaces
the file. The queue holds at most one active and one latest pending capture.
Edit/craft success messages wait for saving; Menu waits before discarding the world.
A failed save keeps the session open for retry. Background saves use a finite iOS
background task; expiration does not promise that the newest change reached disk.
The previous atomic file remains the recovery point if a write is interrupted.
Swift dictionary copy-on-write can still copy storage on the next edit. Startup
load/decode, generation and mesh rebuilding are separate remaining performance work.

Offline loading

Cold launch, Continue and New now read, decode, validate and migrate on a serial
utility loader. The menu shows Loading/Creating Sandbox with Cancel. Continue
waits for pending saves to drain. One loader may execute at a time; cancellation
invalidates its result, and a newer intent waits rather than adding another worker.
Local saves are limited to 16,000,000 bytes on both write and read. Invalid data
fails without replacing the source file; migration does not write until the loaded
world starts successfully. Scene/world construction and meshing still run on main.

Bounded mesh preparation

Terrain preparation uses one serial utility worker and one latest pending value
capture. No mutable live world or SceneKit node crosses to that worker. It creates
a private detached rule model and emits pages of at most 4,096 vertices into a
four-page condition queue. The main actor installs at most two pages per frame.
Nearby chunks prepare first; old chunks remain until replacement starts. Unchanged
network geometry does not restart preparation. SceneKit objects stay on the main
actor. Menu/background cancels stale generations; resume rebuilds current terrain.
On a memory warning the app pauses, cancels prepared work and drops meshes more
than 16 blocks from the player. Resume rebuilds. These caps are initial engineering
limits, not measured physical iPhone memory/frame-time/thermal qualifications.

Fine-grid editing

Grid selects Whole/hit piece,1/2,1/4,1/8 or1/16 collection cubes. Placement always
uses the selected inventory item's actual size. Smaller pieces attach to the aimed
voxel face and snap to the matching subcell grid. Collecting a nonuniform region
asks for a smaller grid; full bags and player-overlap placement reject atomically.
Models stay whole-cell items with their accurate tiny geometry. Online fine edits
require the gateway's fineEdits capability and retain authoritative inventory,
reach, depth and subcell validation. An older gateway needs updating first.
