Sandbox streaming validation and Windows reproduction

The normal frame path calls World.streamAsync with a 1 ms owner deadline. The
existing DetailedMeshScheduler receives the remainder of a 1.5 ms preparation
allowance. Lighting uses the remaining shared FrameBudget.STREAMING_CPU_NANOS
allowance of 2 ms after measured terrain and mesh owner work. Sky capture uses
at most 0.25 ms within that remainder. GPU transfers split into units of at most
64 KiB and at most 2 MiB per frame. These are cooperative deadlines; atomic GL
calls, JVM compilation and safepoints can still overrun a unit. Actual timings
and byte counts are exported rather than treated as hard real-time guarantees.
No graphics defaults, draw distance, resolution defaults or horizon settings
change. The benchmark selects a synthetic Balanced 640x480 profile. The existing
display startup fell back to an actual 1280x720 framebuffer on this assigned
display. Comparisons use actual framebuffer dimensions from each JSON report;
the selected profile and actual viewport are both recorded.

One terrain worker owns its Terrain and Geography caches. It also runs at most
one sky tile batch and one atlas pack, alternating queued sky tasks with terrain
jobs. Sky work does not add another CPU thread or queue behind long GI bakes. Its FIFO retains at
most eight queued/running/completed chunks, including obsolete running work.
The owner may retain one additional result while replaying edits. Base terrain
has at most 4096 full block cells per chunk; fractional authoritative edits are
replayed only on the owner. Jobs contain positions and immutable stress-grid
configuration, never live World maps, model libraries or GL resources.

Sky visibility caches immutable 16x16 tiles. Owner capture checks deadlines
between chunk roots and edited cells. The worker expands/compacts only changed
tiles, then merges packed tiles. World identity, column members, geometry/edit
revisions and model revision fence each result. Packed cache data is capped at
32 MB. A GPU atlas stays active until its replacement, fine nodes, irradiance and
transport are ready. Sky-only updates reuse the existing volume. Two GPU store
generations per role are prepared at startup for normal 96x128x96 lighting and
the supported packed-sky bound. Normal chunk arrivals refill stores; capacity
for exceptional fine-node data grows geometrically. Scratch memory is shared
and bounded at 6 MiB. Retired stores have GL fences polled with zero timeout;
new uploads defer until a store is safe rather than blocking on previous reads.
The pool owns at most 16 textures and two buffers. Its estimated GPU store bytes
include both generations; compare that estimate with its own bounds rather than
assuming equivalence with baseline VRAM estimates that omit lighting stores.
Radiance mip levels are built on the CPU lighting worker. Every level uploads
in slices; no glGenerateMipmap remains in the transport upload path. Shader
formats, mip filtering, visual settings and OpenGL 3.3 remain supported.


Ordinary terrain snapshots copy only immutable roots and six neighbor roots.
Only fractional cells touching a chunk face need fallback border cells; those
are captured incrementally and fenced by the existing mesh revisions. Empty
checks inspect the octree root instead of recursively counting nodes.
Model-library snapshots copy independent lookup maps while sharing registered,
frozen definitions. They preserve IDs and revision without revalidating or
serializing model geometry on the owner thread.
World membership and installed meshes carry a scene revision, replacing the
per-frame resident-map comparison/copy. Moving an empty clustered-light grid
updates its origin without rebuilding its unchanged zero-light GPU stores.

The owning World instance is the session fence: workers cannot attach results.
Travel discards requests outside the active load radius; explicit unload cancels
that position, including an in-progress replay. Replays restart from the current
ordered authoritative history when an edit arrives. Covering newer edits erase
older replayed regions. Existing mesh identity/revision/model fences still
reject stale meshes. A partial ten-chunk column retains distant-parent coverage.
Unloaded collision cells remain solid. Startup draws and polls a loading screen
until the nearby 3x3 columns are resident; respawn uses the regular frame loop.

Windows playtest (physical Windows GPU results are not implied by Linux reports):
1. Build or install the controller's exact feature revision with the existing
   client/launcher pipeline. Keep the same Java version and graphics settings
   for both baseline and feature runs. Use separate synthetic saves/profiles.
2. Use seed 748291. Record resolution, Balanced profile, detailed distance 112,
   horizon 2048, render scale 1, dynamic resolution off, and the GPU/CPU model.
   Keep the same settings throughout. Warm the renderer consistently.
3. F9 starts CSV/JSON timing capture, with video inactive. Walk across fresh
   boundaries, hold flight plus sprint for several minutes, reverse, teleport
   or respawn, then revisit the earlier route. Repeat three fresh-save trials
   for each revision. Separate resident, cold, revisit and transition samples.
4. Compare frame and stream CPU p50/p95/p99, worst frame, 1% lows, >33/50/100 ms
   counts, generation/attachment/edit replay/disposal/scheduling, snapshot and
   upload timings/bytes, lighting/sky/shadow/probe CPU and GPU timings, GC, heap,
   resident geometry estimates, pending counts and oldest job age. GPU timing
   frame EMA is delayed telemetry, not a per-frame GPU distribution.
5. Place/break whole and fractional blocks, RGB LEDs, glass, water and tiny
   models while a second synthetic multiplayer client edits chunk borders.
   Leave and reload the area. Verify current edits, closed borders, shadows,
   light occlusion, collision support and preserved older meshes during swaps.
6. Switch to another seed/world and reconnect; repeat teleport/unload/reload.
   Confirm no old-world chunks or edits appear and shutdown completes.
7. Repeat the route with F10 recording separately. F10 again stops and saves
   the engine MP4. Compare recording overhead against the unrecorded route.
   Never copy account stores or full private runtime logs into evidence.

Linux harness:
  python3 deploy/run_streaming_route.py --display "$DISPLAY" --label LABEL \
    --revision SOURCE --jar EXACT_CLIENT_CLASSPATH
  python3 deploy/run_streaming_matrix.py --display "$DISPLAY"

Build the baseline reproducibly, without changing the checkout or index:
  python3 deploy/prepare_streaming_baseline.py

The matrix requires the saved baseline jar, its timing-only overlay and the
saved feature jar under target/. Use --phase before or --phase after to reuse
completed baseline trials after measured implementation changes. --trials 2,3
selects only those trial numbers. It can run interleaved pairs or separate before/after phases with
fresh synthetic profiles and an identical route. The recorded baseline trials
were completed before the final feature trials. Source and binary hashes are
written to dashboard/evidence/streaming-source-manifest.json. Test commands,
actual distributions, limitations and media are recorded separately as evidence.
